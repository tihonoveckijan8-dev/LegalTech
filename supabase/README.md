# Локальная база данных LegalFlow

SQL-схема и конфигурация Supabase принадлежат репозиторию `tihonoveckijan8-dev/LegalTech`.
Локальная база запускается из этого репозитория. Подключённый удалённый проект `groupp` не используется.

## Требования

- Node.js 22.12 или новее.
- Docker Desktop / Docker Engine запущен.
- Supabase CLI 2.122.1 (запускается через `npx`, глобальная установка не нужна).

## Первый запуск

Из корня репозитория:

~~~bash
npm ci
npx --yes supabase@2.122.1 start
~~~

Команда `start` поднимет локальные сервисы Supabase и PostgreSQL на портах, заданных в `config.toml`. При первом запуске Docker скачает необходимые образы.

Проверить состояние:

~~~bash
npx --yes supabase@2.122.1 status
~~~

## Применение миграций

Локальная база создаётся и миграции применяются командой:

~~~bash
npx --yes supabase@2.122.1 db reset
~~~

Миграции применяются автоматически по имени файла в хронологическом порядке:

1. `migrations/20261110190000_initial_schema.sql` — таблицы, связи, RLS и приватный Storage bucket.
2. `migrations/20261110200000_create_organization_rpc.sql` — безопасное атомарное создание организации и владельца.
3. `migrations/20261111120000_add_audit_triggers.sql` — системный журнал действий по договорам и версиям документов.

SQL-проверки находятся в `tests/001_schema_security.test.sql`. Они проверяют наличие основных таблиц, RLS, grants, аудит-триггеры и политики приватного хранилища.

Команда `db reset` пересоздаёт **локальную** базу и повторно применяет все миграции. Не запускайте её с подключением к удалённой базе.

Проверка SQL на локальной базе:

~~~bash
npx --yes supabase@2.122.1 test db
npx --yes supabase@2.122.1 db lint --local --level error
~~~

Остановка локальных сервисов:

~~~bash
npx --yes supabase@2.122.1 stop
~~~

## Подключение frontend

После `supabase start` CLI покажет локальные API URL и ключи. Заполните локальный `.env.local` на основе корневого `.env.example`:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

Используйте только локальный publishable/anon key. Никогда не помещайте secret или service_role key в переменные `VITE_*`, frontend-код или Git.

## Безопасность и ограничения

- Миграции хранятся в Git; данные локальной базы не коммитятся.
- У каждой организации свои записи, доступ к которым ограничивается RLS.
- Договоры должны храниться только в приватном Storage bucket.
- Приглашения и изменение членства будут реализованы через доверенную серверную логику.
- GitHub Actions проверяет миграции на чистом локальном Supabase stack, запускает pgTAP security tests и проверяет SQL-функции.
- Перед production применением нужно отдельно протестировать доступ пользователей двух организаций, Storage policies и критические сценарии на тестовых аккаунтах.
- Удалённая база не подключается, пока не будет подтверждено, что она именно для LegalTech и выбран подходящий регион размещения.
