# Модель данных LegalFlow

Это проектная спецификация, а не применённая к базе SQL-миграция. Она фиксирует минимальные сущности для первого рабочего сценария.

## Основные таблицы

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| profiles | Профиль пользователя | id = auth.users.id, имя, служебные данные |
| organizations | Компания-клиент (tenant) | id, название, страна, настройки |
| organization_memberships | Членство и роль сотрудника в компании | organization_id, user_id, role, status |
| counterparties | Контрагенты | organization_id, название, регистрационные реквизиты |
| contracts | Основная карточка договора | organization_id, номер, тип, контрагент, сумма, валюта, статус, ответственный |
| contract_versions | Неизменяемые редакции договора | contract_id, номер редакции, путь к файлу, автор, дата |
| approval_steps | Шаги маршрута согласования | contract_id, порядок, назначенный пользователь/роль, решение, срок |
| contract_comments | Замечания и обсуждение | contract_id, автор, текст, ссылка на редакцию |
| contract_tasks | Задачи и обязательства | organization_id, договор, исполнитель, срок, статус |
| contract_documents | Метаданные файлов договора | organization_id, договор, версия, storage path, тип и размер файла |
| audit_events | Журнал действий | organization_id, actor, событие, сущность, дата, метаданные |

## Роли организации

Роль назначается отдельно для каждой организации:

- owner — владелец рабочего пространства и управление участниками.
- director — управленческий обзор и утверждение.
- manager — инициирование договора, работа с контрагентом и редакциями.
- lawyer — юридическая проверка и замечания.
- accountant — проверка финансовых условий.

Роль не является глобальным свойством пользователя. Один человек может иметь разные роли в разных организациях.

## Базовые правила

- Все бизнес-таблицы содержат organization_id.
- Составные ограничения уникальности и внешние ключи не позволяют связывать записи разных организаций.
- Для поиска и списков предусматриваются индексы по organization_id, статусу, ответственному и сроку.
- contract_versions и audit_events работают как append-only история: обычные пользователи не могут изменять или удалять прошлые записи.
- Критические изменения статуса выполняются транзакционно после проверки роли, текущего статуса и ожидающего шага.
- Приглашение участника не должно сводиться к произвольной вставке строки в organization_memberships из браузера. Это отдельный доверенный процесс.
- Поля с персональными данными контрагентов и сотрудников собираются только при необходимости и имеют ограниченный доступ.

## Маршрут первого MVP

1. Менеджер создаёт карточку и первую редакцию.
2. Юрист получает задачу проверки, оставляет замечания или согласует редакцию.
3. Менеджер загружает следующую версию при необходимости.
4. Бухгалтер проверяет сумму, валюту, предоплату и сроки оплаты.
5. Директор утверждает договор.
6. Подписанный экземпляр загружается в приватное хранилище.
7. Система создаёт задачи и напоминания по обязательствам и срокам.

Юридически значимое подписание, бухгалтерский учёт, юридическая экспертиза и интеграция с 1С остаются за пределами первого MVP.

## RLS и Storage

- RLS включается на каждой таблице в доступной через Data API схеме.
- Политики проверяют членство пользователя в той же организации; TO authenticated само по себе недостаточно.
- Доступ к членствам, назначению ролей и системному аудиту ограничивается отдельно.
- Storage bucket с договорами — только приватный. Путь объекта включает идентификатор организации и договора; политика проверяет членство и разрешённое действие.
- Для новых таблиц Supabase нужно явно выдать необходимые SQL-привилегии ролям API: grants и RLS — разные уровни контроля. См. [изменение Supabase Data API от 30 октября 2026](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

Точные SQL-политики будут написаны и проверены в отдельной миграции после выбора выделенного проекта Supabase. До этого документ не является инструкцией для запуска в production.
