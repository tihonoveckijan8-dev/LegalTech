# Архитектура LegalFlow

## Зафиксированный стек

| Слой | Технология | Назначение |
| --- | --- | --- |
| UI | React 19 | Компонентный интерфейс рабочего пространства |
| Язык | TypeScript 5.9 | Проверка типов договоров, ролей и API |
| Сборка | Vite 8 | Быстрая разработка и production-сборка |
| Backend-as-a-Service | Supabase | Управляемый backend для MVP |
| База данных | PostgreSQL | Связанные сущности и транзакционные процессы |
| Авторизация | Supabase Auth | Вход, сессии и идентификация пользователя |
| Файлы | Supabase Storage | Приватное хранение версий документов |
| Серверная логика | Supabase Edge Functions | Приглашения, критические переходы и интеграции |
| Тесты | Vitest | Быстрые модульные тесты |
| Проверка интерфейса | Playwright (следующий этап) | Браузерные сценарии и регрессии |
| CI | GitHub Actions | Автоматическая проверка сборки и тестов |

## Принципы

1. Один frontend, одна PostgreSQL-база и один Supabase-проект для LegalFlow на этапе MVP. Микросервисы и отдельный backend пока не нужны.
2. Организации изолированы на уровне PostgreSQL с помощью Row Level Security (RLS), а не только условной видимостью кнопок в React.
3. Роли хранятся в таблице членства организации. Решения о доступе нельзя принимать по редактируемым данным профиля, локальному состоянию UI или данным из браузера.
4. Документы хранятся в приватном Storage bucket. В PostgreSQL находятся метаданные и пути, но не содержимое файлов.
5. История версий и аудит действий не должны незаметно перезаписываться.
6. Критические действия — принятие решения по согласованию, приглашение участника, изменение состава организации — проверяются серверной логикой и транзакциями.
7. Клиент получает только данные, необходимые текущему экрану. Списки загружаются страницами по 25–50 строк, а не целиком.
8. Realtime подписки добавляются только там, где пользователю важно видеть изменения без перезагрузки. Постоянный polling не используем.
9. Договоры и другие чувствительные документы не кэшируются в браузере офлайн на старте.
10. Сначала реализуются процессы и контроль доступа, затем дополнительные функции: AI, электронная подпись и интеграция с 1С.

## Структура исходников

- src/app — корневой интерфейс и оболочка приложения.
- src/components — повторно используемые UI-компоненты.
- src/features — будущие доменные модули: contracts, approvals, tasks, counterparties.
- src/lib/supabase — создание клиента и общие функции интеграции.
- docs — архитектурные решения и описание данных.
- supabase — конфигурация CLI и миграции после подключения отдельного проекта.

## Переменные окружения

Локально скопируйте .env.example в .env.local и заполните:

- VITE_SUPABASE_URL
- VITE_SUPABASE_PUBLISHABLE_KEY

Publishable key предназначен для браузера и безопасен только вместе с правильно настроенными grants и RLS. Secret/service_role key нельзя добавлять в VITE_ переменные, исходники, GitHub или клиентскую сборку.

## Почему пока без тяжёлых библиотек

- Без Redux: состояние текущего MVP небольшое. Сложный state manager добавим при реальной необходимости.
- Без тяжёлого UI kit: базовые компоненты строятся на обычном CSS.
- Без графиков и анимационных библиотек: они пока не добавляют ценности основному сценарию.
- Без Next.js и NestJS: серверный рендеринг и отдельный backend пока не оправдывают дополнительные слои.

## Этапы подключения backend

1. Создать отдельный Supabase-проект LegalFlow в подходящем регионе.
2. Инициализировать Supabase CLI и создать миграцию через штатную команду migration new.
3. Реализовать схему, grants и RLS-политики, затем проверить их на двух разных организациях.
4. Подключить Supabase Auth и безопасное создание членства через серверный процесс приглашения.
5. Настроить приватный bucket Storage и политики доступа к объектам.
6. Добавить тесты критических сценариев и автоматические проверки.
